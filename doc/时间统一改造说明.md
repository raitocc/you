# 时间统一改造说明

本文面向后端开发，说明时间字段"请求 → 业务 → 入库全链路 Instant"改造的目标、方案、落地结果和遗留事项。改造已完成的范围是 moment、album、media、circle 四个模块，以及信箱（inbox）和"与你有关"（RelatedFeed）的时间收参；gathering、user 的时间字段仍为 LocalDateTime，随各自模块处理。读者凭本文即可理解当前时间处理的口径，无须参考其他讨论记录。

## 现状与目标

改造前有三类重复：

| 重复点 | 改造前 |
| --- | --- |
| 入库换算 | `MomentService.toDatabaseMemoryTime` 与 `AlbumService.toCursorTime` 两份手写转换，circle 内联第三份 |
| 游标时间类型 | `AlbumListCursor` 用 Instant，`RelatedFeedCursor` 用 LocalDateTime，换算口径不一 |
| 审计时间取值 | `LocalDateTime.now(ZoneOffset.UTC).truncatedTo(ChronoUnit.MILLIS)` 散布 20 余处 |

改造后：时间在请求 DTO、业务实体、响应、游标中一律使用 `Instant`；Instant 与数据库列的换算收敛到一个 MyBatis 类型处理器（TypeHandler）；审计时间取值收敛到 `TimeUtils.now()`。两份手写换算已删除，circle 内联的换算一并删除，审计取值在已完成模块内全部走工具方法。

## 关键决策与理由

**数据库列保持 `DATETIME(3)`，不改用 `TIMESTAMP`。** MySQL 的 `TIMESTAMP` 范围是 1970–2038 年，而瞬间的"发生时间"（`memory_time`）允许记录早于 1970 年的回忆，原有代码校验年份 1000～9999 正是为 `DATETIME` 范围而设。存量数据按 UTC 语义读写，无须迁移。

**Instant 与 `DATETIME` 的换算收进全局 TypeHandler。** 类比已有的 `UuidTypeHandler`：写入时 `LocalDateTime.ofInstant(instant, ZoneOffset.UTC)`，读出时 `instant` 由 `LocalDateTime.toInstant(ZoneOffset.UTC)` 得到。注册全局后，实体字段映射和 SQL 参数（`#{...}`）自动走处理器，service 层不再手写换算。

**年份范围校验放在请求入口（service / DTO），不下放到 TypeHandler。** TypeHandler 中抛出的异常会被 MyBatis 包装为 `PersistenceException`，全局异常处理器接不住，参数错误会变成 500。"发生时间超出可保存范围"的校验保留在创建、修改瞬间的入口路径上。当前这项校验处于缺失状态，见"遗留事项"。

**审计时间统一截断到毫秒。** `DATETIME(3)` 只保留毫秒精度；取值时截断（`truncatedTo(ChronoUnit.MILLIS)`），创建响应回显的时间才与再次读出的一致。

## 落地实现

### 全局 TypeHandler

位置 `common/mybatis/UtcInstantTypeHandler.java`，`@MappedTypes(Instant.class)`，由 `application.yaml` 的 `type-handlers-package: com.you.youbackend.common.mybatis` 注册为全局类型映射：

- `setNonNullParameter`：Instant 截断到毫秒后转 UTC 的 `LocalDateTime`，交给 PreparedStatement
- `getNullableResult`（三个重载）：查询结果按 `LocalDateTime` 读出，再 `toInstant(ZoneOffset.UTC)`

注册生效后，字段类型为 `Instant` 的实体属性和 SQL 参数自动经过该处理器。

### 审计时间工具

位置 `common/util/TimeUtils.java`：

```java
/** 取当前 UTC 时间，毫秒精度，供审计字段（createdAt、updatedAt、deletedAt）统一使用。 */
public static Instant now() {
    return Instant.now().truncatedTo(ChronoUnit.MILLIS);
}
```

命名保持中性：删除场景取到的时间写入 `deletedAt`，同一方法服务所有审计字段。

### 实体时间字段

以下实体的时间字段（`createdAt`、`updatedAt`、`deletedAt`，瞬间另有 `memoryTime`）均为 `Instant`：

| 模块 | 实体 |
| --- | --- |
| moment | `Moment`、`MomentImage`、`MomentTag` |
| album | `Album`、`AlbumMoment` |
| media | `MediaFile` |
| circle | `Circle`、`CircleMember`、`CircleShare` |
| inbox | `UserInbox` |

`Gathering`、`GatheringMember`、`AppUser` 仍为 LocalDateTime，随各自模块处理。

### 游标与 Mapper 签名

游标结构中的时间统一为 Instant：`MomentFeedCursor.memoryTime`、`AlbumListCursor.createdAt`、`AlbumMomentCursor.memoryTime`、`RelatedFeedCursor.sharedAt`、`CircleListCursor.joinedAt`、`CircleShareCursor.sharedAt`、`CircleShareMomentCursor.memoryTime`。Mapper 方法签名中表示时间的参数同为 Instant，换算由 TypeHandler 完成，service 层直传。

事件（`MomentDeletedEvent`、`AlbumDeletedEvent`、`GatheringMomentsLinkedEvent` 等 gathering 事件、四个 `Circle*Event`）的时间字段同为 Instant。

## 遗留事项

**年份范围校验缺失（待补）。** 创造、修改瞬间的入口应校验发生时间年份在 1000～9999（`DATETIME` 存得下），游标入口应校验游标时间在可查范围。原校验随手写换算一起删除，当前超范围时间会直打数据库变成 500 而非 400。补法是把年份判断收敛为一个私有方法，在 create/update moment 入口和各分页游标入口调用。代码中以 `// TODO ...缺范围校验` 标出，位置在 `MomentService`、`AlbumService.browseAlbums`、`AlbumService.browseAlbumMoments`、`CircleService`。

**gathering、user 的时间字段仍为 LocalDateTime。** 各自模块改造时迁到 Instant，并把 `LocalDateTime.now(ZoneOffset.UTC).truncatedTo(...)` 换成 `TimeUtils.now()`。

## 验证清单

改造完成后逐项验证：

1. 创建、修改瞬间：`memoryTime` 的响应值与入库值一致（毫秒精度），传入带时区偏移的时间，入库按 UTC 正确换算。
2. 分页翻页：本人瞬间流、时光列表、时光内瞬间、圈子列表、圈子分享、与你有关各分页的首屏、中间页、末页正常；构造 `memoryTime`（或 `createdAt`、`sharedAt`）相同的多条记录，确认游标翻页不重不漏。
3. 删除幂等：删除瞬间、删除时光后 `deletedAt` 正确写入，重复删除直接成功。
4. 超范围时间：提交年份超出 1000～9999 的发生时间，返回 400 参数错误而非 500（当前未实现，见"遗留事项"）。
5. 媒体链路：上传登记、就绪查询的审计时间正常。
6. 信箱链路：同行分享、圈子分享写入 `user_inbox` 的 `shared_at`、`created_at` 为 UTC；成员退出、解散、撤回、内容删除后失效标记时间正确。
7. `application.yaml` 的逻辑删除配置：确认软删除时间由 Java 侧显式写入的路径（当前全部软删走显式 `set`）不受类型变化影响。

## 范围外挂账

以下事项与时间改造无关，记录备查：`registerFile` 对非 UUID 对象键会抛异常导致消息反复入队；上传被拒（超限、类型不合）的对象在 RustFS 无清理归属；`MomentService`、`AlbumService` 中断言提示文案与断言语义不符；`MediaController` 的 `@PathVariable` 冗余名称及遗留 todo 注释。
