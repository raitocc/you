# 文档写作规范

文档应让读者独立理解目标、关键概念和操作方法。精简的对象是重复、铺垫和无关细节，必要的解释、原理与上下文应保留。篇幅以讲清楚为准。

## 1. 文档定位与内容范围

开头简要交代文档解决什么问题、面向什么读者，以及必要的环境或前置条件。正文提供完成理解与操作所需的信息，读者可以从当前文档开始，无须读过聊天记录。

不同文档各自承担明确职责：

| 类型 | 主要内容 |
| --- | --- |
| 通用教程 | 组件概念、接入步骤、核心用法、常用操作及排错 |
| README | 项目概况、启动方式、开发入口与文档索引 |
| 开发约定 | 项目结构、命名、编码风格、业务接法与协作规则 |
| 设计文档 | 目标、业务定义、方案理由、行为规则及必要取舍 |

通用教程采用独立、通用的示例，项目中的具体接法通过链接补充。项目说明则使用实际类名、配置和业务规则，使队友能够据此继续开发。

## 2. 主线与章节组织

每篇文档围绕一个明确目标展开，先建立理解，再说明如何操作。教程通常可以按“概念与职责 → 快速接入 → 核心用法 → 扩展配置 → 故障排查”组织，具体章节随主题调整。

基础、进阶和排错分层放置。读者学习主要流程时，应能连续看完并理解；认证扩展、特殊配置等内容放在相应层次，故障处理集中说明。

标题直接写知识主题或操作内容，让读者看到目录就知道在哪里查：

| 过于笼统或叙事化 | 明确的标题 |
| --- | --- |
| 接下来处理一下令牌 | JWT 解析与验证 |
| 再看看请求怎么进来 | 过滤器中的 JWT 认证 |
| 常用配置 | 交换机、队列与绑定声明 |

标题层级反映内容关系。同一问题放在一起讲，前后章节沿用已经建立的概念。

## 3. 概念、原理与文字讲解

代码不能代替讲解。正文通过连贯的自然语言说明概念是什么、承担什么职责、各部分如何配合，以及关键设计为什么这样做，再用代码展示实现。

例如，讲 JWT 过滤器时，应先解释：过滤器在 Controller 之前读取请求头，验证令牌，把已确认的身份放入请求属性，随后继续请求链；Controller 再从属性中取得身份。这样读者才能理解 `parse`、`setAttribute` 和 `doFilter` 为什么按这个顺序出现。

讲解聚焦关键行为和因果关系。标准赋值、getter 等语法可以由代码表达；认证失败在哪里返回、消息何时确认、签名绑定什么内容等影响使用的行为，需要文字解释。

核心能力应覆盖完整。例如 JWT 包括载荷、生成、解析、过滤器、身份传递与登出；RabbitMQ 包括消息模型、投递与消费；对象存储包括客户端、签名器、基本操作与事件通知。覆盖范围由文章目标决定。

## 4. 代码示例与操作衔接

示例保留完成当前知识点所需的代码。常规 import、重复构造器和其他样板可以省略；容易混淆的类型在对应位置注明包名。

每段示例交代清楚：代码放在哪里，使用的对象和变量从哪里来，如何与前后步骤连接，以及执行后会得到什么结果。片段可以沿用前文的配置、字段和模型，并明确说明沿用关系。代码必须解释，代码本身不能代替教学，解释每一行代码的作用。

同一示例使用一致的名称、数据和配置。前面声明的队列、路由键、字段及模型，后面的发送、消费与排错继续使用同一套名称。

代码后的说明解释关键写法与结果含义。例如说明 `@RequestAttribute` 读取的是过滤器写入的服务端请求属性，比逐行复述方法调用更有帮助。

## 5. 内容密度与详略

篇幅优先用于核心概念、关键流程和常用操作。依赖接入交代用途、版本来源及必要配置即可；涉及行为差异或特殊约束时，再补充原因。

重复提醒合并到最相关的位置。例如 Scalar 与 OpenAPI 的职责在概念部分说明一次，后文直接使用这些术语；签名请求头的一致性在预签名使用处说明。

一段解释一个问题。简单内容直接说清楚，复杂内容分层展开。精简后，读者仍应知道怎么做、为什么以及如何判断结果；必要的原理和步骤衔接保留完整。

## 6. 肯定表达与必要限制

采用直接、肯定的表达，否定起手的句子仅用于必须说明的限制。正文优先告诉读者怎么做，减少反复提醒、假设性风险和过度防御性表述。

| 提醒式表达 | 直接说明做法 |
| --- | --- |
| 不要直接相信客户端传来的用户 ID | 从过滤器验证后的载荷取得当前用户 ID |
| 不要以为队列为零就是没发消息 | 队列为零时，结合发布、投递和确认统计判断处理结果 |

必要限制放在会影响读者操作的位置，并说明具体影响。例如签名绑定了 Content-Type，就交代上传时使用相同值。相同提醒集中出现一次。

## 7. 术语、排版与引用

中英文术语首次出现时对应说明，后文保持一致，例如“交换机（Exchange）”“载荷（Payload）”。同一对象使用固定名称，避免在多个近义称呼之间切换。

类名、注解、字段、配置键和准确的界面标签使用代码格式。原理与因果关系用段落，操作顺序用列表，字段映射和方案比较用表格，跨组件流程可以用简图。

技术结论和版本差异优先引用官方资料，链接放在对应说明附近。引用帮助读者核实与深入阅读，正文仍应把当前问题讲清楚。

## 8. 完稿检查与工作范围

完稿后以首次阅读者的视角通读，重点检查：

- 只看本文，能否理解目标、关键概念和实际做法？
- 核心流程是否完整，文字与代码是否衔接？
- 标题、术语、示例名称和链接是否一致？
- 重复说明和防御性提醒是否已经合并，必要解释是否保留？

普通文档编辑以通读和一致性检查为主。编译、测试或联调围绕明确疑点开展，工作量与任务相称；涉及验证结果时，如实说明实际完成的范围。
